# SECURITY

Growth OS Sync의 위협 모델, 적용된 통제, 의도적으로 수용한 위험, 그리고 **실제 발생한 사고 이력**을 기록한다.
이 문서의 목적은 보안을 주장하는 것이 아니라, 어떤 전제 하에 무엇을 포기했고 무엇이 실제로 깨졌는지 명시하는 것이다.

## 위협 모델

| 항목 | 전제 |
|---|---|
| 사용자 | 1명 (개발자 본인), 기기 2대 (PC · 모바일) |
| 데이터 | 개인 습관 기록, 학습 메모(TIL), 커리어 목표. 금융·의료·자격증명 정보 없음 |
| 자산 가치 | 기밀성은 낮음. **무결성·가용성은 높음** — 기록이 사라지면 도구의 존재 이유가 사라진다 |
| 상정 공격자 | 인터넷의 자동화 스캐너, 배포 URL을 우연히 알게 된 제3자 |
| 상정하지 않음 | 표적화된 공격자, 호스팅 사업자 내부자, 물리적 기기 탈취 |

> 운영 3일차에 데이터 유실 사고가 두 차례 발생한 뒤, 이 시스템의 주된 위험이 기밀성이 아니라 **무결성**이라는 점을 인식하고 위협 모델을 갱신했다. 아래 INC-001 참조.

## 사고 이력

### INC-001 — 낡은 클라이언트 상태에 의한 데이터 유실
**발생일** 2026-09-11 ~ 2026-09-13 (3일간 반복) · **심각도 High** · **상태 해결(2026-09-13)**

#### 증상
모바일에서 기록한 일일 체크와 루틴 항목이 다음 날 소실. 전량 소실이 아니라 **부분 소실**(루틴 4개 중 2개만 잔존)이 관찰되어, 날짜 단위가 아닌 **세션 단위 덮어쓰기**로 추정.

#### 근본 원인
`Last-Write-Wins` 정책에서 **"최신"의 판정 근거가 잘못되어 있었다.**

클라이언트는 상태 JSON에 `_savedAt`(저장 시각)을 심어 비교했으나, 이는 *내용의 최신성*이 아니라 *저장 동작의 시각*이다. 따라서 다음 경로가 성립했다.

1. PC가 앱을 로드하며 서버 GET 시도
2. 무료 티어 인스턴스가 유휴 상태(콜드 스타트)라 GET이 타임아웃
3. **실패를 무시하고** 낡은 로컬 캐시로 앱을 기동
4. 로드 직후 스키마 마이그레이션이 `setState` 호출 → 저장 로직 발동
5. **낡은 내용에 현재 시각이 찍혀** 서버로 PUT
6. 모바일이 저장했던 최신 기록이 소실

즉 **읽기 실패가 쓰기를 암묵적으로 승인하는 구조**였다. 부수적으로, 백그라운드에 남아 있던 앱이 포그라운드 복귀 후 낡은 메모리 상태를 그대로 전송하는 경로도 존재했다.

#### 대응 경과
| 시도 | 조치 | 결과 |
|---|---|---|
| 1차 | 로컬 즉시 저장 + 종료 시 플러시 + `_savedAt` 비교 (I3·I4) | **불충분** — 로드 시점만 방어, 복귀 시점 미대응 |
| 2차 | 복귀 시 서버 재대조 + 로컬 스냅샷 (I5·I6) | **불충분** — 읽기 실패 경로가 그대로 남음 |
| 3차 | **서버 측 낙관적 동시성 제어**(I1) + **읽기 성공 전 쓰기 금지**(I2) + 상태 노출(I7) | 해결 |

#### 교훈
- **분산 상태에서 "최신"의 판정은 클라이언트에 맡길 수 없다.** 최종 권한은 상태를 소유한 서버에 있어야 한다.
- **읽기 실패는 쓰기의 전제 조건을 무효화한다.** 조회에 실패한 클라이언트는 자신이 무엇을 덮어쓰는지 알 수 없으므로 쓰기를 시도해서는 안 된다.
- **조용한 실패(silent failure)가 가장 위험하다.** 동기화 중단이 화면에 드러나지 않아 사용자는 3일간 정상 동작으로 인식했다. 상태 노출(I7)은 기능이 아니라 안전장치다.
- 클라이언트 측 완화만으로 두 차례 실패했다. **서버가 거부할 수 있어야 비로소 통제가 성립한다.**

## 수용된 위험 (Accepted Risks)

### A1. 클라이언트 번들 내 토큰 노출 — 심각도 High
프런트엔드의 `VITE_SYNC_TOKEN`은 빌드 시 JS 번들에 포함된다. 배포 URL을 아는 사람은 개발자도구로 토큰을 추출해 데이터를 읽고 쓸 수 있다.

- **근본 원인**: 서버 세션 기반 로그인 없이 클라이언트가 직접 API를 호출하는 구조
- **수용 근거**: 사용자 1명, 기밀성 자산 가치 낮음. 정식 인증 계층 도입은 스코프 계약(엔드포인트 2개)을 위반
- **보상 통제**: 배포 URL을 적극적으로 홍보하지 않는다. 다만 리포지토리가 공개이고 Vercel-GitHub 연동을 유지하므로 **Deployments 메타데이터를 통해 URL이 노출됨을 인지한다.** 실질적 접근 통제는 URL 비공개가 아니라 `SYNC_TOKEN`에 의존한다 — 이 트레이드오프는 자동 배포의 운영 편익을 위해 의도적으로 수용했다
- **재평가 조건**: 사용자가 2명 이상이 되는 시점

### A2. 저장 데이터 평문 — 심각도 Medium
SQLite에 상태가 암호화 없이 저장된다.
- 수용 근거: 자격증명·금융 정보 없음. 애플리케이션 레벨 암호화는 키 관리 문제를 새로 만든다

### A3. 레이트 리밋 부재 — 심각도 Medium
토큰 무차별 대입과 요청 폭주를 막는 장치가 없다.
- 완화 요인: 토큰이 256비트 랜덤이라 대입 성공은 계산상 비현실적. 크기 제한으로 대용량 공격은 차단
- 재평가 조건: 접근 로그에서 비정상 트래픽이 관측되는 시점

### A4. 감사 로그 부재 — 심각도 Medium
누가 언제 상태를 변경했는지 기록이 없어 침해 시 탐지·추적이 불가능하다.
- 수용 근거: 단일 사용자 환경에서 "누가"는 자명. 다만 **탐지 능력이 0이라는 사실은 인정한다**
- INC-001 조사 시 서버 측 이력이 없어 원인 규명이 클라이언트 코드 분석과 상태 export 파일에만 의존해야 했다. 이는 이 결정의 실제 비용이다

### A5. 무료 티어 디스크 비영구 — 심각도 Low (가용성)
Render 무료 인스턴스는 재시작 시 디스크가 초기화된다.
- 보상 통제: 클라이언트가 전체 상태를 보유하고 저장 시마다 PUT하므로 자동 복구. 주 1회 JSON 백업을 로컬 보관
- 부작용: 유휴 후 콜드 스타트(50초 이상)가 INC-001의 촉발 조건이 되었다

### A6. 동시 편집 시 Last-Write-Wins — 심각도 Medium (무결성)
두 기기를 동시에 열어둔 채 양쪽에서 편집하면 나중 저장이 이전 것을 덮어쓴다.
- **완화 (INC-001 대응)**: 서버 측 낙관적 동시성 제어로 낡은 쓰기는 409로 거부된다. 거부 시 클라이언트는 현재 상태를 스냅샷으로 보존한 뒤 서버 것을 채택한다
- **잔여 위험**: 양쪽이 각각 최신 서버 상태를 읽은 뒤 동시에 편집하면 나중 저장이 이긴다. 항목 단위 병합(CRDT)은 구현하지 않았다
- 수용 근거: 단일 사용자. 항목 단위 병합은 스코프 계약을 벗어난다
- **운영 원칙**: 기기를 전환할 때는 앱을 열고 헤더의 동기화 표시가 갱신된 뒤에 기록한다

### A7. 클라이언트 상태 조작 가능 — 심각도 Low
XP·레벨은 클라이언트 상태이므로 JSON 백업 파일을 편집해 가져오면 임의로 조작할 수 있다.
- 수용 근거: 본인만 사용하는 자기 추적 도구. 조작으로 손해를 보는 주체는 사용자 자신뿐이다. 이 앱의 무결성은 기술적 통제가 아니라 사용자의 정직성에 의존한다

## 운영 수칙

1. 배포 URL을 공개 채널에 게시하지 않는다
2. `SYNC_TOKEN`은 32자 이상 랜덤값을 사용하고, 유출이 의심되면 즉시 교체한다 (Render 환경변수 → Vercel 환경변수 → 재배포)
3. **주 1회 JSON 백업**을 내려받아 클라우드 자동 동기화 폴더 밖에 보관한다
4. 기기 전환 시 동기화 표시가 갱신된 것을 확인한 뒤 기록한다
5. 헤더에 `⚠` 경고가 떠 있는 동안의 기록은 해당 기기에만 저장된다 — 재시도로 연결을 복구한 뒤 계속한다
6. 의존성 보안 권고를 주기적으로 확인한다

## 향후 개선 (우선순위 순)

1. 서버 측 변경 이력 보관 (A4 완화, 최근 N개 버전 롤백 지원)
2. 레이트 리밋 도입 (slowapi 등, IP당 분당 제한)
3. 보안 헤더 추가 (`vercel.json`: `X-Frame-Options`, `Content-Security-Policy`)
4. 의존성 버전 고정 및 자동 취약점 스캔
5. (다중 사용자 전환 시) 세션 기반 인증으로 A1 근본 해결
